- (decision) AD: layered paradigm, feature-packaged. Controller then Service then Repository then H2, with one package per domain (menu/, order/, common/) holding entity, repo, service and controller side by side. Binds all backend units. Prevents a technical-layer split (dto/, entity/, service/) appearing alongside the feature split.
- (decision) AD: single error envelope. Every non-2xx body is ApiError(code, message), a flat two-field record. Framework-level failures are explicitly mapped in GlobalExceptionHandler (MissingRequestHeaderException, HttpMessageNotReadableException, MethodArgumentTypeMismatchException, MethodArgumentNotValidException) so Spring's default timestamp/status/error/path shape never reaches a client. Prevents a client parsing two error shapes.
- (decision) AD: exception messages are the client-facing text. ex.getMessage() feeds ApiError.message for domain exceptions, but is deliberately NOT surfaced for HttpMessageNotReadableException (Jackson parser internals) or MethodArgumentTypeMismatchException (which echoes only the parameter name, never the caller-supplied value nor the target type). Prevents leaking internals through the message field.
- (decision) AD: authorization is enforced in the controller, never the service. MenuController.add and MenuController.delete both open by rejecting any X-Admin value that is not exactly the string true, so null, false and TRUE all fail closed. Services are unaware of admin status. Prevents a second, divergent admin check appearing in the service layer.
- (decision) AD: known and accepted ordering defect. @Valid fires before the controller method body, so an invalid body sent without a valid X-Admin header returns 400 (INVALID_NAME or INVALID_PRICE) instead of 403 NOT_ADMIN. Documented in MenuController. Fixing it needs a HandlerInterceptor. Accepted for v1; a client must not infer authorization state from a 400.
- (decision) AD: state-changing checks run existence, then ownership, then state, in that order. OrderService.cancel throws OrderNotFoundException, then NotOrderOwnerException, then AlreadyCancelledException. Prevents an ownership check leaking the existence of another user's order, and prevents two stories picking different orders.
- (decision) AD: an unavailable menu item is reported as MENU_ITEM_NOT_FOUND / 404, not a distinct code. OrderService.submit throws MenuItemNotFoundException when isAvailable() is false, and that exception's own message reads not found or unavailable. GET /api/v1/menu likewise returns only available items via findAllByAvailableTrue. Unavailability is concealed as absence. Prevents one endpoint inventing MENU_ITEM_UNAVAILABLE while another 404s.
- (decision) AD: GET /api/v1/menu/{id} is the one endpoint returning an item regardless of availability (MenuService.getById uses findById). It is the only way a client can resolve a since-unavailable item's name. Public, no header required.
- (question) BIDIRECTIONAL package dependency, unresolved. MenuService injects OrderRepository (to block deleting a referenced item) and OrderService injects MenuRepository (to validate the item and check availability). menu depends on order and order depends on menu simultaneously. Cross-feature access consistently goes repository-to-repository, never service-to-service, but the cycle means the two packages cannot be extracted independently. Needs either an AD ratifying repository-to-repository reads as the rule, or a decision to break the cycle.
- (decision) AD (frontend): X-Admin is derived from the active router URL by an HttpInterceptor, never from stored state. identity-headers-interceptor adds X-Admin=true only when router.url starts with /admin. This makes admin-header-only-on-the-admin-route true by construction; no component can opt in. Prevents a component setting admin headers ad hoc.
- (decision) AD (frontend): reads use httpResource, mutations use HttpClient. Reads therefore expose isLoading, error and hasValue signals and refresh via reload(); mutations are subscribed explicitly. Prevents two components inventing different loading-state conventions.
- (decision) AD (frontend): the UI renders ApiError.message and never ApiError.code. The single helper apiErrorMessage() in lunch-api.ts is the only place an HttpErrorResponse becomes display text; it falls back to a generic string only when the payload is not an ApiError, with status 0 reported as backend unreachable. Prevents each view formatting errors its own way.
- (decision) AD (frontend): identity lives in one signal, persisted to localStorage via an effect, with every storage read and write wrapped in try/catch so private-browsing mode degrades to a non-persistent session instead of throwing.
- (decision) AD (frontend): the dev server is pinned to port 5173 (npm start runs ng serve --port 5173) and the API is called at the absolute URL http://localhost:8080/api/v1, because WebConfig allows exactly that one origin. A dev-server proxy was the alternative and would make the port irrelevant; the pinned port was chosen to exercise the CORS config that already exists. Prevents a port change silently breaking every request.
- (decision) AD (frontend): all three feature routes are lazily loaded via loadComponent, with a wildcard redirect to the menu route. Three routes only: / for menu plus order form, /orders, /admin.
